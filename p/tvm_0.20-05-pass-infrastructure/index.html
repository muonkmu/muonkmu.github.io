Pass Infrastructure

Relax와 TVM IR은 특정 디바이스에 대해 모델의 성능 지표(평균 추론 시간(mean inference time), 메모리 사용량, 전력 소비량)을 개선하기 위한 optimization pass들을 가지고 있음.
머신러닝 특화 최적화 뿐만 아니라 표준 최적화 셋이 있음

  • constant folding, dead code elimination, operator layout alteration, operator fusion, buffer handling, and loop transformation 등
    각 pass들은 pass 실행 전 또는 수행 중에 수집된 분석 결과를 사용하여 ir-to-ir transformation 형태로 구조화됩니다.
  1. 체계적인 패스 관리의 필요성
  • TVM이 빠르게 발전함에 따라, 이러한 Pass를 보다 체계적이고 효율적으로 관리할 수 있는 방법에 대한 요구가 명백해졌다.
  • TVM Stack의 다른 레이어(Relax, tir)를 가로질러 관리할 수 있는 generic framework는 개발자들이 새 Pass를 쉽게 작성하고 시스템에 통합할 수 있는 길을 열어줍니다.
  1. 기존 컴파일러에서의 영감
  • 이 문서는 아래 두가지의 디자인의 장점을 취한 infra 디자인에 대해 설명함
    • 상용 컴파일러들이 최적화 패스를 관리하는 방식(GCC/LLVM)
    • 레이어를 쌓는 구조에서 현대 딥러닝 프레임워크들이 채택한 방식(PyTorch)
  • 예를 들어, GCC나 LLVM과 같은 기존 컴파일러들은 pass manager를 활용하여 수백 개에 이르는 패스들을 효과적으로 관리합니다. 초기에는 패스 개수가 적기 때문에 수동으로 관리해도 됩니다. 그러나 복잡한 컴파일러일수록 사용자가 패스 실행 순서를 직접 수정하지 않고도 자신만의 커스텀 패스를 쉽게 추가하고 적용할 수 있어야 한다는 요구가 생깁니다.
  • 이와 유사하게, PyTorch나 MXNet Gluon 같은 현대 딥러닝 프레임워크들은 Sequential이나 Block 같은 구조를 통해 레이어를 쌓아가는(pass-style) 구조를 지향합니다. 이러한 구조를 통해, 사용자는 모듈(또는 레이어)을 손쉽게 조합하고 전체 신경망을 구축할 수 있습니다.
  1. TVM의 패스 인프라 설계 목표 TVM의 새로운 패스 인프라는 위에서 언급한 LLVM의 계층적 패스 매니저 구조와 딥러닝 프레임워크의 블록 스타일 컨테이너 구조에서 영감을 받았습니다. 주요 목표는 다음과 같습니다:
  • 최적화의 프로그램적 구성 자동화
    • 사용자가 최적화 파이프라인을 유연하게 구성하고 사용자 정의할 수 있도록 지원
  • 패스 디버깅 편의성 향상
  • 패스 간 의존성 자동 해결
    • 수작업으로 패스 순서를 고민하지 않아도 되도록 지원
  • 개발자가 새 패스를 쉽게 작성
    • Python으로 패스를 작성하고, 이 패스를 TVM 패스 인프라 내에서 자동으로 실행/제어 가능

The Design

우리는 사용자의 확장 용이성(ease of extension)에 중점을 두고 있으며, 사용자가 기존 기능과의 호환성을 해치지 않으면서(backward compatibility) 새 패스를 빠르게 추가할 수 있도록 합니다.
이 설계는 백엔드(backend)와 프론트엔드(frontend) 두 부분으로 구성되어 있습니다.

  • 백엔드(backend)는 패스 인프라의 핵심 로직을 구현합니다.
  • 프론트엔드(frontend)는 사용자가 손쉽게 접근할 수 있는 간단한 API를 제공합니다.(사용자가 자신만의 최적화 파이프라인을 빠르게 생성할 수 있도록 지원)

C++ Backend

TVM은 pass에 필요한 기본 정보를 담을 수 있도록 PassInfo object 를 제공함

  • name : pass의 이름
  • opt_level : 어떤 최적화 레벨에서 패스가 활성화 될지 나타냄
  • required : 해당 패스를 실행하기 위해 선행되어야 하는 패스들( 더 자세한 내용은 include/tvm/ir/transform.h를 참조)
    예를 들어 (향후 더 다루겠지만) pass를 등록하는 동안 Pass 개발자는 name, opt_level, required를 기술할 수 있음.
  • opt_level은 사용자 정의 최적화 레벨에서 특정 패스를 실행할 필요가 있는지를 패스 인프라가 판단하는 데 사용될 수 있습니다.
  • required 필드는 패스 간 의존성(pass dependencies)을 패스 인프라가 자동으로 해결하는 데 활용될 수 있습니다.

PassContext

  1. PassContext는 optimization pass에 유용한 정보를 전달한다.
  • 예) 최적화 실패 원인에 대한 진단 정보를 제공하기 위한 error reporting system
  1. PassContext는 BuildConfig를 대체하도록 설계
  • BuildConfig는 컴파일 옵션(예: 최적화 수준, 활성화/비활성화할 패스 등)을 설정하는 데 사용
  1. 예를 들어, 우리는 opt_level=3에서 수행되는 모든 패스를 실행하면서, PassContext에 지정된 disabled_pass=xx로 일부 패스는 제외시키는 구성을 만들 수 있습니다. 이 경우, opt_level 3에 해당하는 모든 패스를 모은 후, 비활성화된 목록에 있는 패스를 제외하면 됩니다.
  2. PassContext 또한 모든 패스를 계측할 수 있는 방법을 제공합니다.(Pass Instrument 섹션 참)
  3. PassContext class는 유저가 Python with syntax를 편리하게 write 할 수 있도록 설계 (특정 configuration에서 최적화를 수행할 수 있도록)
  4. 유저는 PassContext::Current()를 통해 thread-safe한 방법으로 특정 program scope내에서 사용할 수 있는 context를 획득할 수 있다.(thread-local store인 PassContextThreadLocalStore가 생성된 pass context object들을 유지하는데 사용되기 때)
  5. C++ 및 Python API를 통해 PassContext를 활용하여 컴파일 파이프라인을 생성하는 방법은 뒤에서 예제를 통해 소개됩니다.

class PassContextNode : public Object {
 public:
  int opt_level{2};
  tvm::Array<tvm::Expr> required_pass;
  tvm::Array<tvm::Expr> disabled_pass;
  mutable Optional<DiagnosticContext> diag_ctx;
  Map<String, Any> config;
  Array<instrument::PassInstrument> instruments;
};

class PassContext : public NodeRef {
 public:
  TVM_DLL static PassContext Create();
  TVM_DLL static PassContext Current();
  TVM_DLL void InstrumentEnterPassContext();
  TVM_DLL void InstrumentExitPassContext();
  TVM_DLL bool InstrumentBeforePass(const IRModule& mod, const PassInfo& info) const;
  TVM_DLL void InstrumentAfterPass(const IRModule& mod, const PassInfo& info) const;
  /* Other fields are omitted. */

 private:
  // The entry of a pass context scope.
  TVM_DLL void EnterWithScope();
  // The exit of a pass context scope.
  TVM_DLL void ExitWithScope();

  // Classes to get the Python `with` like syntax.
  friend class tvm::With<PassContext>;
};

struct PassContextThreadLocalEntry {
  /*! \brief The default pass context. */
  PassContext default_context;
  /*! \brief The current pass context. */
  std::stack<PassContext> context_stack;
  PassContextThreadLocalEntry() {
    default_context = PassContext(make_node<PassContextNode>());
  }
};

/*! \brief The thread-local store to hold the pass context. */
typedef dmlc::ThreadLocalStore<PassContextThreadLocalEntry>
     PassContextThreadLocalStore;

Pass Constructs

Pass infra는 계층적 구조(hierarchical manner)로 설계되어 있으며, Relax/TIR 프로그램의 다양한 세분화 수준(granularity)에서 작동할 수 있음
pure virtual class인 PassNode는 다른 최적화 패스의 기반을 제공한다. 이 클래스는 몇몇의 모듈/함수/패스시퀀스 단위에서 서브클래스에 의해 반드시 구현되어야 하는 virtual method들을 제시한다.

class PassNode : Object {
  virtual PassInfo Info() const = 0;
  virtual Module operator()(const IRModule& mod
                            const PassContext& pass_ctx) const = 0;
};
  • 위 functor는 pass가 어떻게 실현되어야 하는지 나타낸다(예를들어 이것은 항상 특정 context 하에서 동작해야 함)
  • 모든 패스는 Module to Module 방식으로 설계되어 있기 때문에, 이 인프라에서 수행되는 모든 최적화는 항상 전체 모듈(IRModule)을 갱신합니다.
    • Module to Module 은 전체 IRModule을 입력으로 받아 최적화 후 새로운 전체 IRModule을 반환하는 방식입니다.따라서, TVM의 패스 인프라는 항상 모듈 전체를 업데이트하며, 이는 패스 간 관리와 확장성에 유리한 구조입니다.

다양한 유형의 최적화 패스를 구현하기 위해 여러 서브클래스가 생성되었으며 (예를 들어 unction-level passes, module-level passes, and sequential passes) 각 서브 클래스 자체가 패스 관리자 역할을 할 수 있습니다.
예를 들어, 자신이 필요로 하는 다른 패스를 수집하고 실행하거나,주어진 메타데이터에 기반하여 패스 간의 의존성 그래프(dependency graph)를 구성할 수 있습니다. 이들 서브클래스의 전체 구현 정의는 src/ir/transform.cc 파일에서 확인할 수 있습니다.
